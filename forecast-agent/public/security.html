Security and privacy

Your sales data, kept apart and encrypted

An overview for IT and security teams. It describes what the service does today; there are no promises here about features that don't exist yet.

Where it runs

Draxly runs on Cloudflare (Workers and Durable Objects). Every connection uses HTTPS, and browsers are told to use HTTPS only (HSTS). The pages use a strict Content Security Policy, and no third-party scripts, trackers or advertising tags are loaded.

Each company's data is kept apart

  • Each company's sales, forecasts, stock levels, connections and activity log live in that company's own separate storage object, never in a shared table.
  • Every request works out the company from the signed-in session or API key, never from anything the browser or caller names. Asking for another company's records by their ID returns "not found". Automated tests cover this.

Encryption

  • In transit: HTTPS (TLS) for every request, including the connections Draxly makes to your systems.
  • At rest: sales figures, product, store and region names, forecasts, accuracy results, stock levels, connection credentials and two-factor secrets are encrypted by the application with AES-256-GCM before they're stored. The key is held in Cloudflare's secret store, not in the code.
  • Some details are stored without application-level encryption because the service needs to search or show them directly: company names, user names and email addresses, upload names, and activity-log entries.
  • When you upload a spreadsheet, it's read in your browser. Only monthly totals are sent; the file itself never leaves your computer.

Signing in

  • Single sign-on with Microsoft (Entra ID) and Google, using OpenID Connect with PKCE. ID-token signatures, issuer, audience, expiry and a one-time nonce are all checked. For Microsoft, Draxly relies on the tenant-verified sign-in name, not the editable email claim; for Google, only verified emails are accepted. Admins can require single sign-on for everyone and choose which email domains may join automatically (as viewers).
  • Two-factor sign-in with any authenticator app (TOTP, RFC 6238), with one-time backup codes. Admins can require two-factor for everyone.
  • Passwords are stored only as salted PBKDF2-SHA256 hashes. The work factor is currently 5,000 rounds, set by the hosting plan's processing limit; it moves to 600,000 rounds on the production plan, and existing users are upgraded at their next sign-in.
  • Limits on guessing: after 5 wrong passwords, two-factor codes or recovery codes, that account waits 15 minutes. Wrong answers look the same whether or not an account exists. Password reset links and invites are single-use and expire after 24 hours and 7 days respectively, and only their hashes are stored.
  • Sessions are random 256-bit tokens that last 30 days. Admins can switch a user off, which ends their sessions immediately, or sign everyone else out at once.

Roles

Three roles, enforced on the server for every request. Every company always keeps at least one admin.

  • Viewer: can see forecasts, stock and reports.
  • Manager: can also upload data, run forecasts and manage stock levels.
  • Admin: can also manage the team, security settings, connections, API keys and the activity log.

Activity log

Draxly records every sign-in (successful or failed), change to users, roles or security settings, upload, deletion, forecast, connection change, sync, API call that changes data, API key change, and email sent. Each entry shows who, when and from which IP address. Admins can view and download the log.

API and connections

  • API keys are shown once and then stored only as SHA-256 hashes. Each key has its own permissions (send sales, send stock, read forecasts), is limited to 120 calls a minute, and can be revoked at any time.
  • Credentials for connected systems (NetSuite, SAP, Dynamics 365, QuickBooks, Shopify, Square) are encrypted at rest and used only to read sales and stock. Ask your administrators to grant read-only access.

Other services we use

  • Cloudflare: hosting, storage and secrets.
  • Resend: sending email (invites, invoices and payment reminders, weekly reports, low-stock alerts), when email is switched on.
  • Microsoft and Google: single sign-on, when you use it.
  • ntfy.sh: the operator's phone alerts. When someone asks for a password reset link, the alert contains their company name and email. When someone sends the contact form or requests access from the demo, it contains the name, company and email they entered.
  • The systems you connect, which Draxly contacts on your behalf.

The open demo

The demo needs no sign-up and shows no sample data. A visitor's spreadsheet is read in their own browser. Only monthly totals per product are sent to Draxly, in small batches, to be forecast in memory and sent straight back. They're never stored, and nothing about them stays after the page is closed.

For each forecast run we record the time, the approximate city and country (from Cloudflare's view of the visitor's network), the type of device, the page that linked to the demo, and the size of the file (number of products and months). We don't record IP addresses, file names, product names or sales figures for demo runs.

Privacy and deleting data

  • Your data is used only to provide Draxly to you. We don't sell it, share it for advertising, or use it to serve other customers.
  • Admins can delete any upload. When an account is closed, all of that company's stored data is deleted: sales, forecasts, stock, connections, the activity log, users and API keys.
  • See the Privacy Policy and the Data Processing Addendum for the details.

Certifications

Draxly doesn't currently hold SOC 2 or ISO 27001 certification. We're happy to complete your security questionnaire: email draxlyforecast@gmail.com.
